# Project analysis

## Goal

Deliver a complete, playable Pac-Man in Python, with an object-oriented and
modular design, a graphics library limited to what MiniLibX offers, a
configuration file, an external maze generator, persistent highscores, a
cheat mode for peer review, and a build published on a public gaming
platform.

## What the subject requires

| Area | Requirement |
|---|---|
| Launch | `python3 pac-man.py config.json`, exactly one argument, no traceback |
| Configuration | JSON with `#` comments, documented keys, robust handling |
| Maze | Generated by the assigned package (not ours), `PERFECT = False`, failures handled |
| Game | 10 levels or more, time limit per level, lives, score, 4 ghosts, pacgums, super-pacgums |
| Interface | Main menu, HUD, pause menu, game over and victory screens, instructions |
| Highscores | Top 10, names of 10 characters (letters, digits, spaces), persistent |
| Cheat mode | Helps the reviewer test every feature |
| Quality | Python 3.10+, flake8, mypy, type hints, docstrings, Makefile |
| Delivery | Public platform (itch.io or Steam), README, this folder |

## Scope

**Must have:** everything in the table above.
**Should have:** unit tests, per-level visual polish, smooth movement.
**Won't have (for now):** sound, animations beyond Pac-Man's mouth, online scores.

## Technical choices and why

| Choice | Why | Alternatives considered |
|---|---|---|
| Python with `pygame`, limited to operations that have an MLX equivalent | MiniLibX was not installed and usable on the development machine (Windows). The subject accepts a similar library if every used function has an MLX equivalent | MiniLibX under WSL or a virtual machine |
| One `Graphics` wrapper, the only file importing `pygame` | Makes the MLX equivalence easy to show and to audit, and the library replaceable | Calling `pygame` from every module |
| Strict configuration with `pydantic` | Typos and wrong values are reported with exact messages and nothing runs with a surprising value | Clamping to defaults, as the subject suggests (see risk R3) |
| Adapter plus validation around the maze package | The package is third party and replaced during review. The game must never crash on a bad maze | Trusting the package output |
| Screens return the name of the next screen | Screens do not depend on each other or on `Application` (no circular imports) | Screens calling `Application` methods |
| Sprites drawn pixel by pixel at the current cell size | MLX cannot resize images, and any cell size must work | Image files in several sizes |
| One `MazeLayout` object per level | Cell size and offsets are tied to a level, so a new level means a new object and nothing stale | Storing them in the renderer |
| Grid movement every 0.15 s, with interpolation when drawing | Simple, testable rules, and continuous-looking motion | Pixel-based movement |
| Tolerant highscore file with atomic saving | The file is not critical, and a crash while saving must not destroy it | Strict failure like the configuration |
| Interface and engine separated | Two people can work in parallel, and the rules are testable without a window | One shared module |
